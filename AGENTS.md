# Cordonix Project Rules

## Purpose and boundaries

Cordonix (`cdx`) provides a typed local execution and workspace contract for AI coding agents. The first backend is Windows C11 with MSVC. A POSIX backend may implement the same public contract later.

The core must not execute command strings through `cmd`, PowerShell, Bash, WSL, or another shell. It may launch an explicitly supplied native executable with a literal argv array. Git, ripgrep, compilers and language tools remain external programs; this project does not reimplement them.

`apply_patch` remains the preferred ordinary UTF-8 source-edit path in Codex. The project’s document core handles strict encoding, hash-checked edits, in-memory sessions and explicit commits for files that need those guarantees.

## Source and document contracts

- Keep program, arguments, working directory, file path, text content, encoding and expected hash in separate fields.
- Reject NULs, line breaks in path fields, code-shaped path values, ambiguous edit counts and stale hashes before writing.
- Preserve raw bytes, BOM, encoding and EOL style. Never use silent replacement or ignored decode errors.
- Keep `dirty_in_memory`, `written_to_disk`, `file_changed`, `unknown`, `timed_out` and `no_match` distinct.
- A timeout after an external mutation may be UNKNOWN; do not automatically retry a mutation.

## AI Agent Constraints

These rules apply to code generation, edits, tests and project documentation. They are implementation constraints, not suggestions to be silently relaxed.

1. **Require evidence before adding defensive complexity.** Do not add code for a hypothetical race or security boundary merely because it is imaginable. Before proposing such a defense, state the concrete failure scenario, estimated likelihood, affected boundary and added code/maintenance cost. Wait for human confirmation before implementing it, and keep the change within the authorized scope.
2. **Validate external data once at the outer boundary.** Parse and validate incoming data at the public entry point, then pass values with confirmed types and invariants through internal functions. Do not repeat the same defensive validation in every internal function unless a new trust boundary is crossed.
3. **Avoid premature abstraction.** Extract a function or type only when it is reused by multiple callers, hides genuinely complex logic, or expresses a clear independent domain concept. Do not create one-use wrappers for visual consistency.
4. **Keep the main path readable.** The main function should show the normal business flow. Move argument checks, edge cases, cleanup details and recovery branches into focused helpers below it, while keeping the normal sequence obvious.
5. **Write only useful comments.** Comments should record an implicit invariant, a counterintuitive decision or a protocol/file-system constraint that the code alone does not reveal. Do not comment obvious variable names, loops or direct assignments.
6. **Regenerate generated files from their source.** For outputs with a generator, template, schema or generation marker, including outputs generated by an AI workflow, change that source or its parameters and regenerate; do not patch the output independently. Ordinary maintained C source authored with AI assistance is source, not a reproducible generated artifact.
7. **Test real behavior.** Tests should exercise the actual implementation and observable result. Do not copy the business algorithm into the test as a second implementation, and minimize mocks where a bounded real fixture or local process gives stronger evidence.
8. **Do not introduce unrelated tools.** Follow the repository’s existing language, build system, dependency set and workflow. A new framework, dependency, generator or process requires an explicit reason, scope and human approval before introduction.

For a new speculative defense or dependency outside the authorized scope, document the smallest proposal and obtain human confirmation. Existing authorized requirements and demonstrated defects can be implemented or repaired without asking the same permission again. Never broaden implementation or dependency changes silently.

## C implementation

- Use standard C11 where possible and isolate Windows APIs in platform files.
- Windows process ownership uses `CreateProcessW`, suspended startup, Job Object assignment before resume, bounded pipe readers and verified cleanup.
- Windows paths use UTF-16 APIs; UTF-8 conversion is strict. CP936/GBK is explicit and round-trip checked.
- File commits use a same-directory temporary file, flush, metadata checks and atomic replacement. Multi-file atomicity is not claimed without a journal or filesystem transaction.
- Avoid unbounded allocations, implicit locale conversions, global mutable caches and process-name cleanup.

## Validation

- Every loop, batch, wait and retry has a small bound, a wall-clock limit and a cancellation path.
- The Windows build uses the verified MSVC path and C11 warnings as errors. Debug validation should include static analysis and sanitizer coverage where the toolchain supports it.
- Test fixtures cover Unicode, spaces, quotes, `$()` literals, newlines, CP936, UTF-8 BOM, CRLF, mixed EOL, stale hashes, ambiguous matches, timeouts, cancellation, descendant cleanup and output limits.
- Codex MCP interoperability is a separate gate from local C unit tests.
- Build with `eng\build.cmd`; the final gate is `eng\test.cmd`, also used by `.github/workflows/ci.yml`. Preserve the existing MSVC C11 workflow. Test binaries and fixtures are owned by `build/` and are not source artifacts.

## Git and delivery

- Preserve unrelated changes and keep generated binaries, `.vs`, build directories, caches and local receipts out of Git.
- Use Conventional Commits after the project has an authorized repository history. Do not commit or publish from the scaffold without explicit authorization.
- Update README, ROADMAP, HANDOFF and CHANGELOG when a public contract or gate changes.
