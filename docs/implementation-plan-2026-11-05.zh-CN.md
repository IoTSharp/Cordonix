## 用户目标与决策权

用户授权把评估落实到路线图，在一个新的实施会话中用多个智能体并行开始完成任务，要求真实闭环。随后强调：不要过度顺从用户或上一轮分析，应根据事实、数据、算法和实际业务独立决定实现与取舍。

因此，三个阶段是方向和依赖框架，不是无条件功能清单。已有能力不重写；能复用的专业引擎先比较复用；没有场景或收益证据的项目保留为待验证。允许纠正、缩小、合并或延期，但必须记录依据，不能把延期项目算作已实现。已经有证据且在授权范围内的工作直接实施，不重复请求许可。

## 决策记录格式

每个交付在修改代码前记录以下六项，优先写入对应专题文档；轻量项目可以写到 HANDOFF 的任务条目：

1. 具体用户任务、可复现输入、当前观察及来源；区分本次实测、历史记录、竞品声明和假设。
2. 现有原生能力/现有外部工具能否完成；是否只需改调用方式或文档。
3. 至少比较“保持现状”“最小扩展”“更大方案”的正确性、往返、输出、CPU/内存和维护成本。
4. 选定合同、兼容方式和简单算法；推导容量和边界，不把经验数字当测量。
5. 用哪些真实入口、输入和可观察结果判定成功；什么证据会推翻选择。
6. 独立复核结论、最终状态、尚未覆盖的边界和后继项。

不为了追求纯 C 重写 Git、rg、编译器、语言服务器、浏览器或文档布局引擎。不因想象中的风险添加新防御、框架或运行时。新增依赖/范围按 AGENTS 的实际规则处理；缺少的批准只阻塞相应项目，不阻塞其他已授权工作。

## 第一阶段：上下文成本和基础任务完整度

### CDX-11A：输出表示，先从已观察的 HTTP 重复开始

首个切片仅增加显式可选的响应表示，保留旧默认合同，保留状态、HTTP code、编码状态、response_complete、remote_outcome、cleanup 等关键证据。原始字节必须有清楚的保留/获取策略；解码失败不能要求重复发送原始网络操作。参数名称和精确错误回退由实施者据代码选择并在动手前冻结。

Base64 长度为 `4 * ceil(n / 3)`；同时输出解码文本和 Base64 会叠加两种表示及 JSON 转义。该公式只说明表示成本，不说明 tokenizer 或任务费用。先用固定的本地 HTTP fixture 比较完全相同响应的两种投影，再报告模型可见体积变化。

第一步不创建通用产物数据库、跨会话缓存或任意字段查询语言。若后续任务确需大结果引用，再独立定义保留期限、读取和失效合同。正确性优先于隐藏错误以压缩输出。

### CDX-11B1：有界多文件读取

目标是合并多次工具往返。复用现有读取模式和编码核心；初版逐文件读取即可，不声称并行 IO 加速。计算复杂度按实际读入总字节估算；峰值内存需把当前解码文件、JSON 聚合结果、协议外层转义全部计入。不能简单把单文件上限乘文件数，也不应为此放大 JSON 输出全局容量。

路径/模式/编码等输入统一在公开边界验证。使用共同 deadline、取消信号、全批字节预算与文件数边界；每个文件保留顺序、状态、来源与范围，未执行项目用 NOT_RUN。真实磁盘单次读失败和整批参数非法分开表达。现有读文件已经支持行/tail/raw，无需重写另一套行扫描。

独立源码复核确认两个必须闭环的边界：当前 `json.c` 的总输出上限为 8 MiB，MCP 又将结果 JSON 转义进 text，因此预算按最终序列化体积核验，加入大量换行、引号和反斜杠的真实文件反例；不得用 32 × 256 KiB 代替预算计算。Windows/POSIX CLI 的异步 worker 分派都要接入新批量入口；同步分支传 NULL cancellation，仅在读取循环里检查取消不足以证明 MCP 取消可用。保留已完成项及未执行项，并用真实通知验证响应和后续会话可用性。

CDX-11B2 的递归树、glob、稳定分页和搜索上下文，先从本地实际调用中选择下一缺口，不把这些不同问题塞进首个批量读取 patch。

### CDX-11C：可复算基线与反例

优先扩展已有 `tests/acceptance`、`tests/protocol` 的测试技术栈；项目现有 Python 只用作验收，不成为产品运行时依赖，不另建测试框架。受控本地 HTTP、Unicode/GBK/BOM/CRLF 文件集、错误状态、大结果限制和取消场景都从真实 cdx CLI/MCP 入口执行。

首先测量正确性、请求数、返回 bytes、elapsed、内存/CPU（仅当已有可靠采样方式）。有现成可用 tokenizer 时记录确切名称/版本和计数；没有时标为 NOT_MEASURED，不以字符数或 bytes/4 冒充 token。真实模型/客户端试验记录 provider usage 和费用口径；不因基准需要擅自购买配额或安装依赖。

普通场景、失败场景和最大预算场景均保留，禁止只挑有利样本。基线确定之后才锁定改善目标；前述评估中的 30%/20% 只是候选目标，不是已承诺收益。至少报告样本数、输入/二进制 hash、调用数、体量、延迟、失败/重试及原文可用性；小样本不宣称统计显著。

既有 `tests/acceptance/benchmark_workspace.py` 可复用其真实入口、正文 SHA 和计数口径；对完全相同语料重复运行，另计完整 MCP 响应的 UTF-8 bytes。必须区分原始正文、工具内部 JSON、最终 MCP 响应三层体积，保留每轮结果；无 provider/tokenizer 数据时，token 与费用仍为 NOT_MEASURED。

### CDX-11D / CDX-11E：能力与互操作

核对源码、构建产物、安装版、MCP schema 和包装清单。需要修复的是本次复现的漂移，不必重写所有历史记录。已有目录创建保留原 ID CDX-09E1；评估技能文件中旧目录/版本描述时以本次事实为准，本任务不自动改个人技能仓库。

MCP 的结构化结果、工具错误映射、版本兼容均先用官方规范与实际宿主验证。上轮报告中的具体协议日期和迁移建议需重新核验适用性，不能只改版本字符串或把“新版”视为足够收益。客户端若同时注入 text 和 structuredContent，需计入两份上下文；无法测量时不声明节省。保留当前可用客户端行为。

## 第二阶段：编程和数据任务循环

- CDX-12A：有限后台任务。先选择真实构建/分析场景，明确开始、状态、增量读取和取消；进程只派发一次。客户端断开、服务端结束、取消后的处理分别验证。有限任务、交互 PTY、浏览器和长期服务属于不同生命周期，不一次混做。
- CDX-12B：单文件多处编辑和 diff，保留 SHA/count、编码/EOL 和显式提交；普通 UTF-8 仍优先 apply_patch。多文件不承诺事务。
- CDX-12C：高频 Git 和构建/测试结果的确定性摘要；保留原始日志位置和失败信号，用原始结果核对，不引入额外模型总结费用。
- CDX-12D：符号检索先比较现有 rg 与 LSP/IDE 后端在目标工程的冷启动、索引、正确性和成本。先覆盖实际高频语言；新增依赖必须有具体成本/范围决定，不默认安装整套语言服务器。
- CDX-12E：按真实 JSON/JSONL/CSV 任务选择字段提取和聚合。结构化处理在本地完成，输出样本/统计/异常；避免为此发明通用 DSL。
- CDX-12F：文件复制/移动/元数据/hash 选择实际缺口，明确覆盖和中断结果，复用已有新建目录和文件合同。

阶段一的度量与结果合同稳定后，按证据连续推进。不存在跨所有项目的固定收益阈值；每项按相同任务的成功率和总成本选择。

## 第三阶段：设计、桌面和办公交付

- CDX-13A：先完成一个实际设计任务的“可编辑源码/资产—本地渲染—局部截图—检查—最终产物”。图像元数据、裁剪、缩略图、对比可评估 Windows 现有原生能力；浏览器由其生命周期 owner 管理。
- CDX-13B：只在具体应用没有合适 API、且 UIA 可暴露有效元素时扩展桌面动作。先证明元素树覆盖率和真实操作回读，再决定泛化范围。
- CDX-13C：为选定 Office/PDF 任务比较已有可用引擎和原生接口，分别验证内容与页面渲染。云端 Figma 或生成模型属于可选能力，不能声称全链路离线。

不先承诺所有文档格式、完整电话音频、全套 UI 自动化和全平台同日完成。决定延期需要写明具体证据与触发重新评估的条件，剩余功能仍为 planned/deferred。

## 并行归属与第一波启动

一个实施主会话，主智能体加三个子智能体。首次派发须写明文件归属；交叉审查在实现结束后交换角色或使用空出的智能体槽，不并发写同一文件。

| A：HTTP 输出 | CDX-11A 决策、最小实现、HTTP 行为测试 | `src/cdx-protocol/http.c`、必要的既有 HTTP 专题和 `tests/protocol/test_http.py` | core 网络/代理机制与全局协议/构建文件，除非主智能体重新分配 |

## 每个切片的闭环

1. 记录问题、现有基线和待推翻的假设，冻结最小合同与所有权。
2. 完成实现、schema/CLI/MCP 接线及真实 fixture；针对失败边界修复而不是调低测试。
3. 独立审查兼容性、数据完整性和收益统计；问题回到负责的实现者修复。
4. 主智能体在最终组合树运行 `eng\build.cmd` / `eng\test.cmd`；涉及共享代码时运行对应 Linux、rg/ext4 门禁。静态分析和 sanitizer 按已有支持与实际修改范围执行；缺失条件保留 NOT_RUN 和具体理由。
5. HTTP 变更还须运行当前 Windows 统一门禁以外的实际 HTTP/代理协议 fixtures。比较原始/新结果与副作用、取消、清理语义，不能仅验证 JSON key 存在。
6. 从新构建二进制独立连接 MCP，回读版本/schema 并执行新增能力；旧安装连接不视作更新后的验收。
7. 验证本地包/文档/例子中受影响范围；更新根文档及专题文档，写完整命令、退出码、binary/source hash 和证据位置。
8. 只有上面实际通过的边界标 PASS。未安装、未发布、没有模型用量等标 NOT_RUN/UNKNOWN，不能用本地 C 通过代替。
9. 在当前授权内继续下一个可行切片；阶段推进无需反复确认。新依赖、对外发布、生产变更或替换共享安装不包含在本轮授权内，需具体结果和既有授权核对后处理。

“启动了子智能体”“写了实现”“测试编译通过”均不等于整阶段完成。首波交付完成也不能把三阶段项目标完成。真实阻塞应明确列出且先完成不受影响的部分；无证据的功能不通过堆代码制造完成感。

## 本轮规划交接

独立只读复核支持首波 HTTP 表示、批量读取和独立基线，并提出上述序列化预算与真实 MCP 取消验收要求。复核基于 `92aba4f` 的 `src/cdx-protocol/http.c:74/87/113`、`operations.c:134/174/571`、`json.c:10/229`、`src/cdx-cli/main.c:64/160/173/194` 和 `tests/acceptance/benchmark_workspace.py:213/264`；后续修改可能改变行号。此复核没有运行构建，也不替代实现后的行为验收。

规划会话只拥有并修改：根 ROADMAP/HANDOFF/CHANGELOG、两份 README 的计划导航、本计划，以及上一轮评估报告的时点澄清。启动实施会话后，根共享文档和源码交由实施主智能体；规划会话不再写这些文件。

本轮不 commit/push/tag/publish，不更换安装版，不执行真实短信/电话/设备/生产网络写操作。历史 HANDOFF 中其他任务的 commit/push/release 授权不转授给本轮。未跟踪的两份计划/评估文档是用户要求的工作成果，应保留并随未来获授权的交付一起处理。
