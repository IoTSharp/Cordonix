评估日期：2026-11-05，Asia/Shanghai。

## 1. 结论与定位

建议把 Cordonix 定位为：**面向 AI 的原生本地执行与上下文工具层，让同一件工作以更少的上下文、更少的往返和更明确的结果完成。**

现有优势集中在执行和文本保真；下一阶段的重点应是输出控制、任务生命周期、精准检索、结构化数据处理和可验证交付。它们直接改善编程、运维、办公和设计任务。

建议先服务 Windows 本地工程工作流，优先覆盖 C/C++、.NET、Java、前端项目及中文旧工程。浏览器、设计和 Office 的专业引擎采用可选适配方式。核心继续保持原生；扩展的运行时和联网需求应明确标注。

本地能力应分清三个边界：工具在本机执行、数据在本机处理、模型在哪里推理。前两项可以由 Cordonix 负责；第三项由客户端和模型配置决定。云端模型仍会接收工具输出，完全离线工作还需要本地模型及本地依赖。

## 5. 我们的优势与短板

### 应继续加强的优势

1. **低运行时负担。** C11 核心和 Windows 系统 API 很适合本地分发。0.1.0 的 SSH 已包含静态 libssh2，因此准确表述是“不要求 Python/Node 运行时”，而非“没有第三方依赖”。
2. **中文工程和混合编码处理。** 显式 CP936、严格往返、BOM/EOL 和 hash 前置条件，对旧工程有实际价值。
3. **执行结果分层清楚。** 退出码、解码失败、超时、取消、清理和未知远端结果分别表达，减少把失败当成功、把结果未知当未执行的误判。
4. **能提供可靠的本机工具边界。** literal argv、进程所有权、内存/磁盘区分、单文件提交组合得较完整。进程所有权并不是 OS 权限隔离，文档已明确这一点。[L1–L4]
5. **设备和工程现场适配。** 串口、旧编码、跳板 SSH 和手机接入适合真实工程现场；应作为可选能力组保留。

### 优先解决的短板

1. **节省 token 还未形成产品机制和证据。** 内存复用降低重复加载，原样返回的文本仍进入模型上下文。
2. **基础任务需要多次调用拼装。** 多文件读取、搜索后取上下文、单文件多处编辑、运行后摘要都缺少直接的批量入口。
3. **长任务跨不过客户端单次调用期限。** 当前调用有服务端时间限制，但客户端可能先断开；同时其它工具请求会被 active worker 阻塞。[S2]
4. **数据表示重复。** HTTP 同时回传正文及 Base64，通用 MCP 层再把 JSON 作为 text 包装；大结果容易挤占上下文。[E1][S2]
5. **编程语义和设计/办公产物链不足。** 文件操作无法直接回答“这个函数有哪些调用者”或“导出的页面是否排版溢出”。
6. **平台、协议和交付状态不够统一。** 当前目录、安装版、远端开发版不同；通信工具的平台覆盖不同，文档中的历史状态也混在一起。[E2][L3]

## 6. 本次直接测量：HTTP 结果存在可避免的重复

通过当前 0.1.0 的 `http` 读取 Desktop Commander 官方 README，收到 HTTP 200。本次一次性观察如下：

| 项目 | 观察值 |
|---|---:|
| 服务器响应体 | 52,594 bytes |
| 解码后正文 | 52,394 JavaScript 字符单位 |
| 同时返回的 `body_base64` | 70,128 字符 |
| MCP text 内整个结果 JSON | 130,479 JavaScript 字符单位 |

这是实际返回表示的体量比较，**不是 token 数、费用或延迟基准**。它仍足以支持一个优先改进：保留原始字节的可获取性，但允许调用者只向模型提交正文、摘要、特定字段或产物引用。

兼容方式应采用新增可选参数，例如 `detail` / `representation` / `fields`，或版本化的精简结果合同；不能直接删除 0.1.0 已发布的字段。二进制和解码失败仍需保留原始数据回看路径。先让调用者显式使用精简模式，验证后再决定默认值策略。

大结果建议返回：操作状态、关键摘要、截断/完整性、原文句柄、hash、下一页游标。原文保留在本地，后续按需取片段；不得以摘要静默覆盖错误和未完成状态。

Anthropic 关于 MCP 效率的公开分析指出，工具定义和中间结果反复进入上下文是两类成本来源。[S12] Cordonix 可以先采用有界批量和确定性字段选择，无需为了组合调用引入一套任意脚本解释器。

| 按需求 / NET-01 | SSH 常见认证/算法与目标寻址兼容；SFTP 增量完善；Linux 按需求补齐 | 提高已有通信能力的实际覆盖率 | M–L | 用真实目标组合建立兼容矩阵，优先复现实际失败场景 |

MCP-01 有具体差异依据：固定远端提交仍返回 `protocolVersion=2025-06-18`，依赖 initialize；MCP 2026-07-28 已改用每请求版本/能力元数据及 `server/discover`。[S2][S13] 需要兼容矩阵，不能仅替换版本字符串。旧版协议也定义了 `isError`、`structuredContent` 和 `outputSchema`；结构化结果是互操作改进，不自动意味着更省 token，若客户端同时注入两份结果反而可能更大。[S14]

JOB-01 先服务有限编译和分析任务。交互式 PTY、浏览器、开发服务器是后续不同生命周期合同，不应通过放松现有 `execute_program` 的清理行为实现。

EDIT-01 保留普通 UTF-8 修改优先用 `apply_patch` 的现有约定。多文件先给出逐文件结果和冲突信息；没有 journal 或文件系统事务时不承诺全有或全无。

## 8. 编程、日常工作和设计的目标工作流

| 任务 | 建议形成的完整流程 | 模型只需要重点看到 |
|---|---|---|
| 修复构建错误 | 启动构建任务 → 提取诊断 → 定位符号 → 修改 → 重跑 → 产物/测试回读 | 错误、对应函数、实际改动和最终验证 |
| 理解代码库 | 按文件名/类型发现 → 符号概览 → 指定引用/片段 → 必要时展开 | 与问题相关的结构和证据 |
| 汇总业务数据 | 本地读取 CSV/JSON/表格区间 → 过滤/聚合 → 输出表格或报告 → 回读 | 样例、统计、异常和产物路径 |
| 设计网页 | 读取设计变量/组件 → 生成可编辑源码 → 浏览器渲染 → 局部截图/布局检查 → 调整 | 相关组件、局部视觉结果及可打开页面 |
| 制作办公文件 | 内容提取 → 按结构修改 → 导出 → 页面预览 → 检查内容和排版 | 变动区域、溢出/缺字体/错页和最终文件 |
| 运维排障 | 连接诊断 → 只读采集 → 本地结构化摘要 → 必要的授权动作 → 状态回读 | 关键指标、诊断依据和动作后的结果 |

设计方向建议优先完成“看得到、改得动、导得出、验得到”。生成图像本身可以由专业模型/应用提供；Cordonix 承接资产、本地执行、图像处理与交付证据。Figma 能作为可选云端协作对象；离线设计路径以本地 HTML/SVG/图像和本地渲染器为基础。[S8][S10]

Office/PDF 的页面布局、字体和渲染是另一类问题，不能仅以文本提取成功声明交付正确。原生核心加可选专业适配，比同时自建所有格式渲染器更符合当前规模。

## 9. 如何证明更省 token、更高效

建议至少建立以下任务集：Unicode/空格路径找文件、GBK 修改、10 文件定点读取、大 JSON 取字段、失败构建日志、长时间测试、大仓库引用定位、网页视觉修复、CSV 汇总、文档导出验证。

分两层测量：

1. **确定性工具层**：同一输入比较原始结果/精简结果 bytes、指定 tokenizer 的 token、调用数量、处理耗时、原文可恢复性。
2. **代理任务层**：固定模型版本、提示和初始状态；比较宿主默认工具、Cordonix 0.1.0、改进版；选择适用的竞品参与部分场景。重复有限轮次，报告失败与人工介入，避免只挑成功样本。

记录字段至少包括：task/model/client/version、成功率、首轮成功率、重试数、input/output/cached tokens、费用、工具调用数、墙钟时间、异常退出、结果未知、产物 hash。对无 provider usage 的环境，只报告 tokenizer 估算，不将字符数冒充 token 数；工具输出统计也不能代替整轮模型成本。

可讨论的阶段目标：在选定任务集上，工具结果 token 中位数下降至少 30%，总往返下降至少 20%，任务成功率与关键错误可见性不下降。**这两个百分比是候选验收目标，不是预测或已实现收益。** 延迟同时报告中位数、P95 与样本量；价格、缓存和计费口径单列。

优先度可用任务频率 × 每次可避免的上下文/往返 × 成功率改善，除以开发与维护成本来判断。用观察值更新，不预先填入貌似精确的分数。

## 10. 分阶段交付与范围控制

**第一阶段：建立低上下文成本的基线。** 完成版本/能力核验、输出表示选择、批量读取与检索、协议兼容、真实任务计量。已有目录创建进入正常发布验收。

**第二阶段：完成编程任务循环。** 有界后台任务、日志诊断、单文件批量编辑、优先语言的符号查询、JSON/CSV 本地投影。选择同一组真实项目验收“找得到—改得对—跑得完—结果清楚”。

**第三阶段：扩展设计和办公。** 先接入浏览器/图像预览与文档渲染，再按真实任务选择原生 UIA 和文件格式适配。Linux 完整度与 macOS 后端根据目标用户需求排序。

暂缓事项：更多缺少真实用户场景的协议、完整电话音频栈、向量数据库或内置模型服务、通用脚本语言/任意工作流 DSL、全量 Office/浏览器内核重写，以及没有实测依据的“更快/节省 90%”宣传。

建议按启动配置提供 coding、operations、desktop、device 等能力组合，只发布选中的工具集合；让客户端在支持时按需发现。避免简单把所有操作塞入一个超大 `action` schema，因为参数空间和使用说明也会消耗上下文。配置分组应保留默认兼容性，并测量宿主实际加载了多少定义。[S6][S8][S12]

核心交付原则：原生本机处理、类型化输入、有限执行、原文可回看、结果可验证；每增加一个接口，都说明它替代了哪个高频步骤，以及如何减少完整任务成本。
